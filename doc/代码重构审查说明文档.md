# 代码重构审查说明文档

> 用途：把一段已生成的 Python 代码做 Review + 重构，移除不符合规范写法，对齐我们的编程约束。
>
> 底层风格目标：**C 式直白流程、节点式函数思想，输入输出清晰、便于日志断点排查，仅第三方库强制 class 可保留，业务逻辑全部使用普通函数。**
>
> 一条元规则贯穿全文：每写一条代码，先问“这是**值**还是**状态**？能不能**一眼机械判定**？”——含糊留给人现场判断的，都是规则的漏洞。

---

## 一、本次重构任务说明

你需要对提供的 Python 源码做代码审查，标记问题，然后输出**改造后的完整代码**。
审查、修改严格遵守下面全部规则，逐条检查源码里每一处代码，识别不符合规范的代码并重构。

## 二、审查 & 重构规则（逐条校验）

### 1. Class 类相关检查（最高优先级）

1. 如果是**ORM 模型类（SQLAlchemy/Peewee 等第三方库强制要求）**：允许保留，**但是必须删除写在类内部的所有业务计算方法**，业务逻辑抽成外部独立普通函数，ORM 类仅用来定义数据表字段。
2. 如果是**业务自定义 class（自己封装业务逻辑、业务方法的类）**：属于违规，**全部拆除**。把类里面的业务方法改为独立普通函数；类中保存的数据，改为函数显式传入的参数。
3. 第三方 SDK 自带实例对象（数据库连接、客户端实例）可以保留，不必拆类 / 改结构；但作为运行期状态，仍须按 §2.2 显式入参（禁止模块级全局偷偷读取）。
4. 仅用于描述数据外形的 `@dataclass(frozen=True)` / `TypedDict`，**不属于**第 2 条要拆除的“业务 class”（见 §6.1）。

### 2. 框架魔法与隐式状态检查（红线项）—— 先分“值”与“状态”

规则不是“一律禁全局”，而是按**值的来源**分两类——**写死在源码里的字面量**，还是**来自外部配置 / 环境、可能在部署或运维期被改动**；各走各的通道：

1. **硬编码字面量常量**（相等容差、日期窗口天数、字段名等**写死在源码里的口径**）：允许模块级定义，但必须——集中在最内层“原语层”文件、命名全大写、字面值静态可追、判定层只读不改。
2. **来自外部 / 环境的运行期状态**（数据库连接、HTTP 客户端、凭据、时钟、随机源、外部配置、**按环境切换的 workflowId**）：**禁止**函数从模块作用域偷偷读取，必须作为**显式入参**逐层传入（手动依赖注入）。判据不看“进程内会不会变”，看“值是不是从外部注入”——外部注入的配置进程内也不变，仍须传参。
3. 一并清理的历史红线（全部删除 / 重构）：自定义业务装饰器、手写反射、动态代理、自制 IOC 容器、AOP 切面相关业务逻辑；隐式上下文、线程本地变量等不进参数就获取的隐藏数据。

> 判断一句话：这个值是**写死在源码里的字面量**，还是**来自外部配置 / 环境**？**来自外部 → 必须传参；写死的字面量 → 可作模块级常量。** 二者不可混用同一条规则；“进程内会不会变”不是判据，否则外部注入的固定配置会被误判成可模块级的常量。

### 3. 函数改造规范

1. 遵循单一职责：一个函数只做一件事，超长函数拆分成多个短小函数。
2. 区分两类函数：
   - 纯计算函数：无 IO、无网络、无数据库读写。保证**相同入参一定得到相同输出**，不修改传入原始数据，无副作用。
   - IO 函数：数据库读写、文件、FTP、网络请求。IO 操作收拢到外层边界，**不能和核心业务计算混写在同一个函数**。
3. **平铺硬阈值**（消除“这算不算嵌套”的争议）：单个表达式内条件/三元嵌套 **≤ 2 层**，列表推导 **≤ 2 层**；第 3 层必须提为具名子函数或改为顺序赋值。多情况的措辞 / 取值一律写成顺序 `if … return`，**禁止链式三元挤在一个 `return` 里**。
4. **连续转换写成管道**：对同一数据做多步转换，优先让值依次流过若干单参数纯函数（顺序赋值或一个极小的 `pipe(value, *steps)` helper），而不是层层括号包裹。
5. 抽象阈值与**反向复用义务**：
   - 只把重复 ≥ 3 次的逻辑抽公共函数；删除提前过度抽象、为优雅而做的泛化封装。**本条只约束“同一段逻辑被复制多次”的场景，不适用于 §3.6 的分派表与 §7 的分层结构**——那两类是结构要求，与重复次数无关。
   - **已抽出的纯 helper，同类逻辑禁止在调用处就地重写**（“先抽了函数、又有分支绕过它复制同一逻辑”视为违规）。
6. **数据驱动分派，禁止 if/elif 判类型链**：按类型 / 规则码分多分支处理时，**分支数 ≥ 3** 用一张显式 `key → 函数` 的表加循环分派；只有 2 种分支时按 §3.3 写成顺序 `if … return`，不强制建表（与 §3.5「重复 ≥ 3 才抽」、§7.7「不为拆而拆」对齐，避免为两个分支造表 + 两个单行函数的过度拆分）。新增一条处理 = 加一个函数 + 在表里加一行，**不改动已有分支**。

### 4. 调试能力改造 —— 纯函数杜绝日志，日志只在 IO / 编排层

出入口日志**只加在 IO 边界函数与编排函数上**；**纯函数杜绝添加任何日志**——`debug` 级、入参 / 返回值打印、分支埋点，`logger` 一行都不许有（保持无副作用、可 `assert` 直跑，见 §7.6）。**这是硬约束，不是偏好**：约束对象是 §3.2 定义的**纯计算函数**——凡纯计算函数，函数体内不得出现 `logger`；**编排函数无论本身是否做 IO 均可打日志**，因为它负责代下游纯函数收口入参 / 返回值（见下条），不得用「不碰 IO 即禁日志」误伤非 IO 的编排收口函数。

- IO / 编排函数：入口打印全部入参，出口打印返回结果；只看出入参就能定位 bug，不需要理解框架底层。
- 纯函数的可观测性由**编排层收口**：编排函数调用完整批纯函数后，打印一次“入参摘要 + 各返回值标识”，而不是往每个纯函数里塞 `logger`。
- **机械判据**：函数体里出现 `logger.*` ≡ 这里必须是 IO / 编排层。纯函数里出现 `logger` 即为违规，**日志上移到调用它的编排函数**，不在原处保留。

### 5. 异常与错误处理

1. 禁止静默捕获、吞噬异常（空 except 不处理）。
2. 异常显式捕获、显式抛出；报错信息附带触发异常时的**输入数据**（对外可展示结论时，附带单号 / key 级定位摘要，不整包塞入原始 payload，避免凭据与明细外泄）。

### 6. 数据结构 —— 契约强制，而非可选

1. **跨函数传递的结构化数据（上下文、返回体）必须有显式外形声明**：`TypedDict` 或 `@dataclass(frozen=True)`，只定义字段、**不含业务方法**。禁止用裸 dict + 字符串 key 在函数间传业务数据（key 打错会静默失败）。
2. pydantic / dataclass 仅用来描述数据外形，不要在里面写业务方法。
3. 数据结构尽量扁平化，不写复杂嵌套结构。

### 7. 可审计性（AI 审计的 token 成本）—— 与上面六条同等重要

> 为什么单列一条：代码是给 AI 审计员读的。**审计某类问题必须读进来的行数，就是这段代码的长期成本。** 单文件超过 ~400 行之后，哪怕只审一句文案，也要把整个文件付一遍 token。

1. **单文件 ≤ 400 行**（不含文件头 docstring）。超了按**已有的分层边界**切文件；不按函数切、不为每个函数建文件、不按 HTTP 动词/实体拆。某一层自身超线且无第二层可借时，允许拆成**同层的多个文件**（如 `判定_a.py` / `判定_b.py`），仍视作一层。
2. **固定五层，一文件 = 一层职责**：`路由 → 编排 → {判定（只算 pass / 布尔）, 话术（只拼展示字符串）} → 原语（常量与小工具）`；判定层与话术层**互不 import**，由编排层并列调用。IO 函数归**编排层**文件（满足 §7.5 的分文件要求，不另设 Layer）。分层表写在该文件头 docstring：哪层在哪个文件、**审计哪类问题该读哪个文件**。
3. **超线时优先在“判定 vs 话术”边界切**：判定文件不出现面向用户的整句措辞，话术文件不含任何 `pass` 计算。审“结论对不对”只读判定层，审“话说得对不对”只读话术层。
4. **依赖单向**：路由 → 编排 → {判定, 话术} → 原语，禁止反向 import。最内层原语/纯函数区**禁止 import 会引入 IO、日志或运行期状态的库**（`logging`、DB 驱动、HTTP 客户端、配置读取一律不许；纯函数杜绝日志，见 §4），标准库纯计算模块（`math`、`re`、`datetime` 类型等）允许；仅注解需要时用 `TYPE_CHECKING` 引入。使“这个文件不可能有 IO、也不可能打日志”一眼可断言，审计时不必追调用链。
5. **IO 与纯函数分文件**，不只是在同一文件里分区——分区靠肉眼，分文件靠 import。
6. **纯函数自检能直接跑**：`test_*.py` 里用 `assert`，`python tests/test_x.py` 不装 pytest、不连 DB 就能跑，让“改文案有没有破”用一条命令替代逐行推演。
7. **不为省 token 而牺牲可读性**：拆分只做在真实的分层边界上（见第 2、3 条），不为拆而拆。判断标准一句话：**按这个文件切完，审计某类问题时能少读吗？能就切，不能就不切。**

## 三、输出交付格式（固定）

1. 【代码审查问题清单】：逐条列出原代码里面不符合规范的问题，标明代码位置，简要说明为什么不符合。
2. 【重构思路】：简要写改造方案。
3. 【重构完成代码】：输出完整可运行 Python 代码，保持原有业务功能不变，只调整代码组织形式。

## 四、重要约束

> ⚠️ 业务逻辑、业务算法**不能改动**！只改代码组织、代码形态、代码结构。输入输出结果必须和原来代码完全一致，不能改变原有功能。

## 五、简短精简版本

> 适合直接粘贴在 prompt 里，快速发起代码 review。

任务：审查并重构下面这段 Python 代码，**业务功能保持完全不变，仅调整代码结构，对齐我们的编码规范**。

规范清单：

1. **Class**：仅 ORM 类（第三方强制）可留，只定义字段、删类内业务方法；业务 class 全拆成独立函数，数据改为入参。仅描述数据外形的 frozen dataclass / TypedDict 不属此列。第三方 SDK 实例可留（但连接 / 客户端仍须显式传参，见第 2 条）。
2. **魔法与状态**：分两类——**写死在源码里的字面量常量**（容差 / 窗口天数 / 字段名）可模块级，须集中原语层、全大写、静态可追；**来自外部 / 环境的状态**（连接 / 凭据 / 时钟 / 配置 / 按环境切换的 ID）禁止读全局，必须显式传参。删自定义装饰器 / 反射 / AOP / 自制 IOC / 隐式上下文。判据看值来源：写死的字面量→可模块级；外部注入（进程内不变也算）→必须传参。
3. **函数**：单一职责，长函数拆短；区分纯计算函数（无 IO、同入参同输出、不改入参、无副作用）与 IO 函数（收拢外层）。平铺硬阈值——条件/三元、列表推导嵌套 ≤ 2 层，第 3 层提具名函数或顺序赋值，禁链式三元塞进 return；连续转换写成管道。重复 ≥ 3 次才抽函数（此阈值只管重复逻辑，不管 §7 的分层与分派表），**已抽的 helper 禁止就地重写**；分多类型处理——分支 ≥ 3 用显式 `key→函数` 表 + 循环、禁 if/elif 判类型链，2 种分支写顺序 if。
4. **日志**：出入口日志只加 IO / 编排函数；**纯函数杜绝任何日志**（含 debug 级、入参/返回值打印、分支埋点），由编排层调用完整批后统一打印一次“入参摘要 + 结果标识”。判据：函数体出现 `logger` ≡ 该处必须是 IO / 编排层，纯函数里即为违规，日志上移编排层。
5. **异常**：禁静默吞异常；捕获时附带当时的输入数据（对外展示只带单号 / key 级摘要，不整包塞原始 payload）。
6. **数据模型**：跨函数传的结构化数据必须 `TypedDict` / `@dataclass(frozen=True)` 描述外形、不含方法；禁裸 dict + 字符串 key 传业务数据；结构扁平。
7. **可审计性（token 成本）**：单文件 ≤ 400 行；固定五层（路由 / 编排 / 判定 / 话术 / 原语），一文件一层，头 docstring 写“审哪类问题读哪个文件”；超线优先切“判定 vs 话术”边界；同层超线可拆成同层多个文件；依赖单向——编排并列调用判定与话术、两层互不 import，最内层不 import 会引入 IO / 日志 / 运行期状态的库（含 `logging`——纯函数杜绝日志），标准库纯计算模块可用；IO 与纯函数分文件（IO 归编排层）；纯函数自检写成能直接跑的 `test_*.py`（不依赖 pytest / DB）；拆分只做在真实分层边界，不为拆而拆。

输出格式：先列出原代码违规问题清单，再写重构思路，最后输出完整改造后的 Python 代码。**业务逻辑不能修改，运行结果和原版完全一致。**
